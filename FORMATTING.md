# Formatting and Style Conventions (PDF)

`PETITION.md` is the single source of truth; `Petition_for_Rulemaking.pdf` is a rendered artifact and should never be hand-edited — regenerate it with `python3 build_pdf.py` (see `README.md`) after any markdown change, and a GitHub Actions workflow (`.github/workflows/build-pdf.yml`) also does this automatically on push. The PDF's look is modeled on a real Petition for Rulemaking / Request for Waiver filed with the FCC (Association of American Railroads, filed by Hogan Lovells) that the user supplied as a reference, plus standard legal-filing rules the user gave directly. Any future change to `PETITION.md`'s structure should preserve these conventions unless the user says otherwise:

- **Page**: US Letter, 1in margins on all sides (keeps the printed text area within the required 6.5 x 9.5in). Wide tables get their own **landscape**-oriented pages instead of cramming into the 6.5in portrait width — see "Landscape tables" below.
- **Font**: Times New Roman (serif fallback), 12pt minimum everywhere the substantive text appears, **including footnotes' body text** — this was an explicit user rule, even though the real reference filing actually uses smaller footnote text. This does *not* extend to the small superscript locator numerals themselves (`.fnref`, `.fnnum` — 8pt): those are locator marks, not "the footnote," in every real filing examined, and the user's own follow-up bug report confirmed 12pt superscripts read as a defect, not a requirement.
- **Spacing**: double-spaced body text (`line-height: 2`), left-aligned (not justified). Paragraphs are first-line indented (`text-indent: 0.5in`) with no extra gap between paragraphs (`margin: 0`) — spacing comes from the double line height alone, matching the reference filing's continuous flow. Exceptions with `text-indent: 0`: the front-matter block, the signature block, blockquotes, list items, and lettered sub-lists (`.sublist`). The front matter and signature block are also single-spaced (`line-height: 1.15`), like a real filing's cover page and closing block — only the substantive numbered-paragraph body is double-spaced.
- **Caption**: centered, bold — "Before the / FEDERAL COMMUNICATIONS COMMISSION / Washington, DC 20554" (per explicit user correction; an earlier draft had this plain-weight, matching the reference filing, but the user asked for bold) — followed by a borderless two-column "In the Matter of" table with the docket/RM number. That table's first column should be roughly half the row width so the ")" column lands near the center of the page, matching the reference filing.
- **Document title** (e.g. "PETITION FOR RULEMAKING" — one word, matching the rest of the document's usage; do not let it drift to "RULE MAKING"): centered, bold, with generous (`~2.5em`) margin above and below, matching the reference filing's blank-line spacing.
- **Section headings (I., II., ...)**: left-aligned, bold, upper case (`text-transform: uppercase` in CSS — the markdown source itself stays mixed-case for readability).
- **Lettered subheadings (A., B., ...)**: left-aligned, bold, indented (`margin-left: 0.5in`), title case (no uppercase transform).
- **Lettered sub-lists within a paragraph** (e.g. "Adopting such a rule would: a. ... b. ..."): write these as plain, non-indented markdown paragraphs inside a `<div class="sublist" markdown="1">` wrapper, indented via CSS `margin-left`. Do **not** indent the source lines with leading whitespace — four-space indentation is Markdown's *indented code block* syntax, and the whole list will silently render as a monospace `<pre><code>` block instead of styled text. This happened once during drafting.
- **No decorative color/shading** — black text and rules only. The one deliberate exception: proposed rule-text redlines use `<u>underline</u>` for insertions (standard legislative drafting convention, not decoration).
- **Non-breaking spaces in every legal citation token**: within citation strings like "FCC 99-84", "WT Docket No. 95-57", "14 FCC Rcd 8812", pilcrow pin cites ("¶ 13", "¶¶ 12-16"), and CFR/USC citations ("47 C.F.R. § 97.3", "5 U.S.C. § 553(e)"), use `&nbsp;` between every word/number that belongs to the same citation token, so it can't wrap mid-citation across a line break (e.g. "FCC&nbsp;99-84", "WT&nbsp;Docket&nbsp;No.&nbsp;95-57", "14&nbsp;FCC&nbsp;Rcd&nbsp;8812", "¶&nbsp;13", "47&nbsp;C.F.R.&nbsp;§&nbsp;97.3"). Covers: FCC order numbers, docket numbers (WT/PR/GN Docket No.), Rcd reporter citations, ¶ pin cites, the title-number-to-abbreviation gap in "NN C.F.R."/"NN U.S.C.", the abbreviation-to-§ gap, and the §-to-first-number gap. Started scoped to "FCC filings" only, then extended to CFR/USC citations too on user follow-up — when in doubt, extend rather than leave a citation type unprotected. After adding/editing any such citation, re-run the same regex-based sweep rather than hand-placing `&nbsp;` (see the commits that introduced this for the exact patterns) — it's easy to miss instances by hand across a document with dozens of citations.
- **Web-page citations get a URL and access date; official legal citations don't.** Any footnote citing a regulator's website, an agency guidance page, or a news article should include the live URL and "(last visited [date])". Citations to CFR sections, FCC orders, ITU Radio Regulations, and other formally-published legal authorities are left in standard Bluebook-style citation form (reporter/docket number) — courts and agencies don't cite their own orders with a URL, and adding one there isn't standard practice.
- **Every URL in a footnote must be a real, explicit `<a href>` hyperlink, not bare text.** The build script auto-linkifies every bare `https://...` substring found in footnote text (see the `linkify()` regex sweep right after footnote extraction in `build_pdf.py`) — do not rely on a PDF viewer's own URL auto-detection instead. That auto-detection is unreliable and was observed truncating a real citation URL mid-path (stopping at an underscore in a directory segment, silently dropping the actual filename), producing a link that looked plausible but pointed at the wrong, incomplete address. After adding any new footnote with a URL, verify the *actual* embedded link target (not just that clicking it does something) via pypdf: iterate `page['/Annots']`, filter `/Subtype == '/Link'`, and print each `/A['/URI']` to confirm every citation's full URL is present verbatim.
- **Primary sources belong in `sources/`**, not just cited by URL/title. When the user supplies (or you obtain) the actual PDF of something cited in the petition — an FCC order, an ARRL filing — add it to `sources/` with a descriptive filename (date + docket/party + short description) and index it in `sources/README.md` against exactly which petition paragraph/footnote cites it. If a supplied document turns out **not** to be relevant to any citation (this happened once — a document initially thought to be ARRL's 2010 comments turned out to be an unrelated 2014 ex parte letter), delete it and remove its reference entirely rather than keeping it "for the record" — don't accumulate cruft in the sources directory.
- **Footnotes**: real page-bottom footnotes via WeasyPrint's CSS `float: footnote`, not endnotes. The build script extracts python-markdown's `[^N]` footnote definitions and re-injects each one as (a) a small (8pt) superscript `<sup><a href="#fn-N" id="fnref-N">N</a></sup>` at the point of reference, immediately followed by (b) `<span class="fn" id="fn-N">` containing a matching `<a href="#fnref-N">N</a>` back-link plus the footnote text — both are real, clickable links, not CSS-generated counter content, so a reader can jump both directions in the PDF. Two easy-to-reintroduce bugs to watch for on any footnote-CSS change:
  - WeasyPrint auto-generates its own `::footnote-marker` (at the footnote's landing spot) and `::footnote-call` (at the reference point) by default; both must be explicitly suppressed (`content: normal`) or the real link text gets a second, unstyled, duplicate number rendered right next to it. This shipped as a real bug once (silently doubled every footnote number in the document) before being caught and fixed.
  - Do **not** put `line-height: 0` on the `.fnref`/`.fnnum` anchor elements themselves. It was carried over once from the old CSS-pseudo-element design (where it made sense) and, once these became real `<a>` elements, collapsed their PDF link annotation to a **zero-height clickable rectangle** — visually correct, completely unclickable. Verify link hit-testing after any footnote CSS change by inspecting `page['/Annots']` rects via pypdf, not just by eyeballing the rendered page.
  - A rule separating the footnote area from body text is drawn once per page via the `@footnote` page-margin box (`@page { @footnote { border-top: ...; } }`), not per-footnote — do not set a `width` on that box, since it's the actual footnote content area, not just a decorative header; constraining its width also badly wraps every footnote's text.
- **Table of Contents**: dotted-leader entries with **live page numbers**. Use WeasyPrint's native `leader(dotted)` generated-content function for the dots and a separate `target-counter(attr(href), page)` span for the page number — **not** flexbox or CSS table-cell display for the row layout. Both of those box-layout approaches were tried and broke the leader whenever an entry's label text wrapped to two lines (the dotted line either vanished or only spanned the last line); `leader()` flows as part of the same inline text run as the label, so it naturally continues on whichever line the label ends. Needs the `toc` markdown extension purely for its side effect of giving headings predictable slug `id`s to link against — its own generated `<div class="toc">` output is unused and stripped.
- **Landscape tables**: a table too wide for comfortable portrait columns (e.g. Table 1's six columns) gets its own landscape-oriented pages via WeasyPrint named pages — `@page landscape { size: letter landscape; ... }`, `.landscape-table { page: landscape; }`, and (critically) `body { page: normal; }` on the default named page. Without that last rule, WeasyPrint keeps appending normal-flow content onto the last-used page orientation after the landscape block ends, instead of returning to portrait. Also set `tr { break-inside: avoid; }` globally — without it, a table row can split across a page break with some of its cells' content on one page and blank cells on the next (this happened once, dropping an entire row's data). Give the table a numbered, centered caption (e.g. "**Table 1. ...**") as the first paragraph inside the `.landscape-table` wrapper div.
- **Numbered paragraphs**: the substantive numbered paragraphs (`1.`, `2.`, ...) in `PETITION.md` must have the period **escaped** (`1\.`, `2\.`) — a bare `21. text` at the start of a line is parsed by python-markdown as an ordered-list item, and a new `<ol>` silently restarts numbering at 1 every time a heading interrupts the list. This bit twice during drafting; always verify with a script that greps the *rendered* PDF text for sequential paragraph numbers, not just the markdown source, after any edit that adds/moves/renumbers paragraphs. The same verification script should also check footnote definitions for duplicates/orphans (a `[^N]` referenced with no matching definition, or vice versa) — both paragraph and footnote renumbering are highly error-prone when done by hand and should be done with a small renumbering script (shift old numbers to temporary placeholders first, then to final numbers, to avoid collisions) followed by the verification script, every time.
- Raw HTML blocks in the markdown (e.g. `<div class="frontmatter" markdown="1">`) need `markdown="1"` and the `md_in_html` extension, or nothing inside them (headings, tables, bold, etc.) gets processed as markdown.
- **CJK glyph support**: some footnotes quote non-English source text verbatim (e.g. the Japanese original of the MIC "memorial stations" page, German statute text). The `font-family` stack in every rule includes CJK fallbacks (`"Hiragino Mincho ProN"`, `"Hiragino Sans"`, `"Noto Serif CJK JP"`, `"Noto Sans CJK JP"`) after the Times New Roman/serif chain, and the GitHub Actions workflow installs `fonts-noto-cjk` alongside `fonts-liberation` for this reason. Without a CJK-capable font available at build time, those characters silently render as blank boxes instead of failing loudly — always spot-check any newly-added non-Latin-script quote by rendering the actual page as an image, not just by confirming `pdftotext` can extract the text (extraction succeeding says nothing about whether the glyphs actually painted).
- **Repeat citations reuse the same footnote number** (explicit user instruction). Write `[^N]` again wherever a source is cited a second time; do not add a new "*See* note N, *supra*" footnote. python-markdown gives repeat calls ids like `fnref2:N`; `build_pdf.py` converts every call, emits the floating note text only at the first call, and makes later calls link to that note. (An earlier build converted only `fnref:N`, which left repeat calls as broken blue links with no note on their page; the build now fails if any call is left unconverted.) Keep footnote numbers in order of first citation.
- **Footnote on the wrong page.** Stock WeasyPrint, when a paragraph reaches the bottom of a page and breaking before the current line would violate `orphans`, pushes footnotes whose calls are already on that page to the next page to make room for one more line (`report = ...` in `weasyprint.layout.block._linebox_layout`). The result is a call on one page and its note on the next, with no warning. `build_pdf.py`'s `disable_footnote_pushback()` rewrites that one line to `report = False` at build time, so the paragraph is broken or moved instead, and exits with an error if the source line no longer matches (for example after a WeasyPrint upgrade). The GitHub Actions workflow pins `weasyprint==70.0` for that reason; if you upgrade, re-check the patch. After rendering, the build also checks that every `fn-N` note is on the same page as its first call (`fnref-N`) and fails if not. (An earlier workaround retried different widows/orphans settings until one happened to work; that treated the symptom and needed a 24-page layout, so don't bring it back.) The `footnote-policy: line` on `.fn` is still needed for footnote calls inside table cells.
